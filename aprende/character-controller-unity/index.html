Character controller en Unity: separar las físicas de los estados

En el anuncio de Project Sargon conté que el character controller me llevó semanas. Lo más difícil fue organizar una máquina de estados que funcionara bien sin que cada estado tuviera que ocuparse de la gravedad. Aquí explico cómo lo separé.

Alberto Blanco · 9 de noviembre de 2026

Lo cuento por encima en el vídeo del anuncio. Aquí va más a fondo, con código.

El nombre confunde

Unity tiene un componente que se llama CharacterController, y es fácil pensar que con añadirlo ya tienes el personaje hecho. El componente es solo una base de físicas y de movimiento. Se encarga de las colisiones, las rampas y los escalones, y poco más. Ni siquiera aplica la gravedad si usas Move.

Un character controller de verdad es mucho más que eso. Es todo lo que decide cómo se mueve y reacciona tu personaje, con sus estados, el input, las animaciones y, en un juego como Project Sargon, el combate.

Dos formas de empezar

Para la parte física hay dos caminos. Uno es usar un Rigidbody con un collider y programar a mano el comportamiento. Tienes fuerzas, empujones y todo el motor de físicas a tu favor, pero también tienes que pelearte con la fricción, las rampas y los rebotes que no quieres.

El otro es partir del componente CharacterController. No reacciona a fuerzas, pero resuelve bien las rampas y los escalones, y el movimiento hace exactamente lo que le pides. A cambio, la gravedad y cualquier empuje los calculas tú.

En Project Sargon uso el componente, tanto en el prototipo como ahora. La separación que explico después vale igual con un Rigidbody.

Cómo lo hice la primera vez

En un juego de exploración la gravedad tiene que afectar al personaje siempre, esté en el estado que esté. En el prototipo lo resolví metiéndola en la clase base de los estados.

Cada estado tenía su UpdatePhysics y al final llamaba a base.UpdatePhysics(). Ese método de la clase base comprobaba si el personaje tocaba el suelo, llevaba el coyote time, cambiaba al estado de salto o de caída, aplicaba la gravedad, movía al personaje y actualizaba el animator. Algo así:

public class State
{
    public virtual void UpdatePhysics()
    {
        // Suelo, coyote time, paso a salto o a caída, gravedad,
        // Move y animaciones. Todo aquí, para todos los estados.
        _player.velocity.y += _player.gravity * Time.deltaTime;
        _player.controller.Move(_player.velocity * Time.deltaTime);
    }
}

public class AttackState : State
{
    public override void UpdatePhysics()
    {
        _player.velocity.x = _player.velocity.z = 0f;
        base.UpdatePhysics();   // sin esta línea, el personaje flota
    }
}

Funcionaba, pero tenía sus problemas:

  • La gravedad dependía de una línea. Cada estado nuevo tenía que acordarse de llamar a base.UpdatePhysics(), y en el orden correcto.
  • La clase base decidía transiciones. El paso a salto o a caída estaba en la base, mezclado con las físicas, así que cualquier estado podía acabar saltando aunque no tuviera sentido.
  • Todos tocaban la velocidad. Los estados escribían directamente en la velocidad del personaje, y para saber quién la había cambiado había que revisarlos uno a uno.

Dos capas

Para la versión de ahora separé el personaje en dos partes.

  • Las fuerzas van en un componente propio, ForceReceiver. En su Update aplica la gravedad, el impulso del salto y los empujones, sin saber en qué estado está el personaje.
  • Los estados deciden cuánto quiere moverse el personaje por su cuenta. Ninguno calcula la gravedad.
[RequireComponent(typeof(CharacterController))]
public class ForceReceiver : MonoBehaviour
{
    private const float GroundedVerticalVelocity = -0.5f;

    [SerializeField] private float _drag = 0.3f;

    private CharacterController _controller;
    private float _verticalVelocity;
    private Vector3 _impact;
    private Vector3 _dampingVelocity;

    public Vector3 Movement => _impact + Vector3.up * _verticalVelocity;
    public bool IsFalling => _verticalVelocity < GroundedVerticalVelocity;

    private void Awake()
    {
        _controller = GetComponent<CharacterController>();
    }

    private void Update()
    {
        if (_controller.isGrounded && _verticalVelocity < 0f)
            _verticalVelocity = GroundedVerticalVelocity;
        else
            _verticalVelocity += Physics.gravity.y * Time.deltaTime;

        // Los empujones se van apagando solos
        _impact = Vector3.SmoothDamp(_impact, Vector3.zero, ref _dampingVelocity, _drag);
    }

    public void Jump(float speed) => _verticalVelocity = speed;
    public void AddForce(Vector3 force) => _impact += force;
}

La velocidad vertical es solo suya. Un estado puede pedirle un salto o meterle un empujón, pero lo que pasa después lo decide este componente. Como no depende del jugador, el mismo componente me sirve para cualquier personaje que tenga que caer o recibir golpes.

La máquina de estados

La máquina de estados es pequeña. Cada estado tiene su Enter, su Tick y su Exit.

public abstract class State
{
    public abstract void Enter();
    public abstract void Tick(float deltaTime);
    public abstract void Exit();
}

public abstract class StateMachine : MonoBehaviour
{
    public State CurrentState { get; private set; }

    public void ChangeState(State next)
    {
        CurrentState?.Exit();
        CurrentState = next;
        CurrentState?.Enter();
    }

    private void Update() => CurrentState?.Tick(Time.deltaTime);
}

Un solo sitio para moverse

La clase base de los estados del jugador tiene un método Move. Suma lo que quiere el estado y lo que traen las fuerzas, y llama al CharacterController. Si el personaje ha empezado a caer, también lo pasa al estado de caída, para que ningún estado tenga que vigilarlo.

public abstract class PlayerBaseState : State
{
    protected readonly PlayerStateMachine _stateMachine;

    protected PlayerBaseState(PlayerStateMachine stateMachine)
    {
        _stateMachine = stateMachine;
    }

    // La única forma que tiene un estado de mover al personaje
    protected void Move(Vector3 motion, float deltaTime)
    {
        if (_stateMachine.Forces.IsFalling && _stateMachine.CurrentState != _stateMachine.FallingState)
            _stateMachine.ChangeState(_stateMachine.FallingState);

        Vector3 velocity = motion + _stateMachine.Forces.Movement;
        _stateMachine.Controller.Move(velocity * deltaTime);
    }
}

Y así lo usan dos estados:

public class PlayerFreeLookState : PlayerBaseState
{
    // ...

    public override void Tick(float deltaTime)
    {
        Vector3 movement = GetCameraRelativeMovement();
        Move(movement * _stateMachine.RunSpeed, deltaTime);
    }
}

public class PlayerAttackingState : PlayerBaseState
{
    // ...

    public override void Tick(float deltaTime)
    {
        // No se desplaza, pero sigue cayendo y recibiendo empujones
        Move(Vector3.zero, deltaTime);

        // ...avanzar el ataque y decidir a qué estado volver
    }
}

La diferencia con el prototipo es que la clase base ya no hace las físicas. Las fuerzas se calculan siempre en su componente, llame quien llame a Move. Si un estado nuevo se olvidara de moverse, el personaje se quedaría quieto y se vería enseguida. Con el prototipo, el fallo era que flotaba solo en ese estado.

Detalles a tener en cuenta

  • Un empujoncito hacia abajo en el suelo. Si la velocidad vertical se queda en cero al tocar el suelo, isGrounded parpadea entre un frame y otro. Por eso el componente de fuerzas deja un valor negativo pequeño mientras estás apoyado.
  • Crear los estados una vez. Se crean en Awake y se reutilizan. Si haces new en cada cambio de estado, generas basura y es más fácil dejarte suscripciones colgando.
  • Las transiciones las decide cada estado. La única excepción es la caída, que va en Move porque puede pasar en cualquier momento.

Lo que viene

El combate de Project Sargon va encima de esta base. Cada estado nuevo pide su movimiento con Move, y la gravedad sigue funcionando sin que tenga que acordarme de ella.
