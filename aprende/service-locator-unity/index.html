Service locator en Unity: cómo organizo los sistemas de mi juego

Pasé meses sin enseñar nada de Project Sargon porque estaba montando la base del juego. Es un core framework en el que los sistemas se conectan a través de un service locator. Aquí cuento cómo lo he hecho en Unity.

Alberto Blanco · 9 de noviembre de 2026

Lo conté en este vídeo del devlog. El artículo va un poco más a fondo, con código.

El problema

En un juego hay sistemas que usa casi todo lo demás, como el input, el audio o el guardado de partidas. Una puerta tiene que sonar al abrirse y el menú de opciones tiene que guardar lo que cambias.

Si cada script busca esos sistemas por su cuenta, con FindFirstObjectByType o con un singleton distinto en cada clase, el proyecto se llena de referencias cruzadas. Al principio funciona. Luego cada mecánica nueva cuesta un poco más que la anterior, y un cambio en el audio rompe algo en el menú de pausa.

Qué es un service locator

Es un registro central. Cada sistema se registra una vez al arrancar el juego, y cualquier script lo pide por su tipo. El script que lo pide no necesita saber quién lo creó ni en qué objeto está.

La versión mínima es un diccionario que va de un tipo a una instancia:

using System;
using System.Collections.Generic;

public static class Services
{
    private static readonly Dictionary<Type, object> _services = new();

    public static void Register<T>(T service) where T : class
    {
        if (_services.ContainsKey(typeof(T)))
        {
            UnityEngine.Debug.LogError($"{typeof(T).Name} ya está registrado");
            return;
        }
        _services.Add(typeof(T), service);
    }

    public static T Get<T>() where T : class
    {
        if (_services.TryGetValue(typeof(T), out object service))
            return (T)service;

        UnityEngine.Debug.LogError($"{typeof(T).Name} no está registrado");
        return null;
    }

    public static bool TryGet<T>(out T service) where T : class
    {
        bool found = _services.TryGetValue(typeof(T), out object obj);
        service = obj as T;
        return found;
    }
}

La mía tiene algo más, como poder sustituir un servicio o comprobar si existe, pero la idea es esta.

Registrar los servicios al arrancar

Todo empieza en una escena 0_Bootstrap, la primera de la lista de Build Settings. Tiene un único objeto con un Bootstrapper que no se destruye al cambiar de escena. Registra los servicios y luego carga el menú principal.

[DefaultExecutionOrder(-100)]
public class Bootstrapper : MonoBehaviour
{
    private void Awake()
    {
        DontDestroyOnLoad(gameObject);

        // Primero los que no dependen de nadie
        Services.Register(new SaveService());
        Services.Register(new AudioService());
        Services.Register(new InputService());
        Services.Register(new SceneService());

        SceneManager.LoadScene("1_MainMenu");
    }
}

El orden importa. Si un servicio necesita a otro al inicializarse, tiene que registrarse después. Por eso el guardado va el primero.

Los servicios propios del juego los registro en otro componente, al lado de este. Así el framework no sabe nada del juego y lo puedo reutilizar.

Arrancar desde cualquier escena en el editor

Lo anterior tiene una pega. En el editor casi nunca le das a Play desde la escena de Bootstrap. Le das desde el nivel que estás tocando, y ahí no hay servicios.

Lo resuelvo con un método que Unity llama antes de cargar la primera escena. Si no estamos en la escena 0, apunta dónde estábamos y carga Bootstrap. Cuando el Bootstrapper termina, nos devuelve a la escena original.

public static class AutoBoot
{
    public static int SceneToReturnTo = -1;

    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.BeforeSceneLoad)]
    private static void LoadBootstrapFirst()
    {
        int current = SceneManager.GetActiveScene().buildIndex;
        if (current == 0) return;

        SceneToReturnTo = current;   // el Bootstrapper vuelve aquí al terminar
        SceneManager.LoadScene(0);
    }
}

Usarlo desde cualquier sitio

A partir de ahí, cualquier script pide lo que necesita:

public class Door : MonoBehaviour
{
    [SerializeField] private AudioEventSO _openSound;

    public void Open()
    {
        Services.Get<AudioService>().Play(_openSound);
        // ...
    }
}

La puerta no tiene una referencia al AudioService en el inspector ni lo busca en la escena. Si cambio cómo funciona el audio por dentro, no hay que tocar la puerta.

Detalles que me han ahorrado problemas

  • Limpiar el registro al entrar en Play Mode. Si desactivas el Domain Reload para que el editor vaya más rápido, las variables estáticas sobreviven de una partida a otra. Hay que vaciarlas a mano:
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
private static void ResetStatics()
{
    _services.Clear();
}
  • Liberar los servicios en orden inverso al salir. Guardo el orden de registro y al cerrar lo recorro al revés. Así cada servicio se cierra antes que aquellos de los que depende.
  • No dar error mientras el juego se cierra. Al salir, siempre hay algún objeto que pide un servicio que ya no está. Con un indicador de que la aplicación se está cerrando, ese error deja de llenar la consola.
  • TryGet para lo opcional. Si una escena de prueba no tiene configurado el audio, el juego sigue sin sonido en vez de romperse.

Inconvenientes

El service locator tiene mala fama en algunos sitios. Las dependencias quedan escondidas, porque mirando la clase Door desde fuera no sabes que usa el audio. Y si te olvidas de registrar un servicio, el error salta al ejecutar el juego y no al compilar.

La alternativa más habitual es la inyección de dependencias, con librerías como VContainer o Zenject. Para un juego que hago yo solo, me compensa la sencillez del service locator. Para que no se convierta en un cajón de sastre, solo registro sistemas que de verdad son globales. Lo que pertenece a un nivel o a un enemigo se queda en su sitio.
